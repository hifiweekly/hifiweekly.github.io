Design: launch latency changes after ej-prj-3-job2 #

This doc continues launch_latency_consolidated_design.md, which stops at ej-prj-3-job1. It covers the changes made since, and §11 lists what that doc now gets wrong.

1. Summary #

With all the changes through ej-prj-i2-5, a 6-node sky jobs launch on kind drops from 69.9 s to 41.1 s (−28.8 s) against the fork point 5ef55efa4, and every candidate run beat every base run. Changes 6 and 7 then cut the wait after SUCCEEDED from 4.3 s to 2.6 s (p = 0.0002). Client total went from 41.3 s to 40.0 s, which isn't significant (p = 0.19).

  • Provisioning is where most of it comes from. Phase D halves, from 29.6 s to 14.7 s. It's mainly the bytecode image and the fixes before it.
  • The controller no longer sits on a finished job. RUNNING → SUCCEEDED falls from a random 8–15 s to about 0.1 s.
  • Users don't get the full gain yet. These runs use a locally built bytecode image and imagePullPolicy: IfNotPresent set in the task. The template still sets Always, and the image isn't published.
  • Phase A swings between about 3 s and about 7 s for a reason not yet found (§8.4). Compare arms within one run, not across runs.

3. Design #

3.1 Change 1: precompile bytecode in the image #

Full design: precompile_runtime_bytecode_design.md.

Problem. uv doesn't compile bytecode by default, so every pod compiled Ray and its dependencies on first import.

Fix. Add --compile-bytecode to the runtime install in Dockerfile_k8s and Dockerfile_k8s_gpu.

Cost. The image grows from 1.67 GB to 1.83 GB. The build compiles 10,736 files in 2.60 s.

What stays uncompiled: the Ray files that apply_patches.py changes, and the SkyPilot wheel installed at pod start.

3.2 Change 2: lazy Ray Serve import #

Where: sky/skylet/ray_patches/scripts.py.diff and scripts.py.patch, apply_patches.py.

Problem. ray start imported ray.serve.scripts only to register the ray serve command, which pulled in pandas and FastAPI on every pod, before GCS started.

Fix.

  • A patch to Ray's scripts.py registers a _LazyServeCli group, which imports Serve only when ray serve is used.
  • apply_patches.py used to import each module to find its file, which would have imported Serve just to patch the file that avoids it. It now uses importlib.util.find_spec, which doesn't run the module.

3.3 Change 3: watch pods between polls #

Where: _wait_for_pods_to_run in sky/provision/kubernetes/instance.py.

Problem. The wait slept 1 s between polls, so a launch noticed its last pod about 0.5 s late on average.

Fix. The sleep is replaced by a wait that ends early when every waiting pod is running or a pod is going away.

  • The poll still decides. The watch only ends the wait; the poll that follows makes every decision, so failure handling is unchanged.
  • A watch failure falls back to sleeping out the rest of the interval.

3.4 Change 4: exact job timestamps over gRPC #

Where: sky/schemas/proto/jobsv1.proto, sky/skylet/services.py, sky/jobs/utils.py, SKYLET_VERSION 44.

Problem. GetJobSubmittedTimestamp and GetJobEndedTimestamp returned a protobuf float, which holds a current Unix time only to the nearest 128 s. With SKYPILOT_ENABLE_GRPC on, a managed job's times were off by up to about a minute, and a short job's duration was recorded as 0 s.

Fix. Add an optional timestamp_double to both responses, and keep setting the float for older clients. When a skylet doesn't set the new field, the client reads the exact value through the existing head command.

gRPC is off by default, so this doesn't affect any benchmark in this doc.

3.5 Change 5: end time with the status #

Where: sky/jobs/controller.py, recovery_strategy.py, utils.py, sky/skylet/job_lib.py.

Problem. After a job ended, the controller ran two head commands (status, then end time), and the log follower ran its own status check. Without gRPC, each is a kubectl exec of about 1.6 s.

Fix.

  • The combined head command (get_job_status_and_timestamps) also returns the end time.
  • A launch that saw the job succeed hands its status and end time to the monitor loop, which then needs no head command.
  • The monitor loop's status check also returns the end time, so a finished job doesn't fetch it separately.
  • The follower trusts a tail exit code of SUCCEEDED, and reads the recorded status every 0.2 s until the controller writes it.

Side effect. Phase H grew from 2.48 s to 3.84 s, because the controller saves the logs after SUCCEEDED, and the client now reaches that wait sooner. Changes 6 and 7 address this.

3.6 Changes 6 and 7: shorten the wait for saved logs #

A wait trace of ej-prj-i2-5 showed where phase H's 3.9 s went:

Step in H Time Source
Client polling for the saved logs (1 s sleeps) 2.00 s Traced; overlaps the two rows below
Controller's head command to find the log directory 1.54 s Traced
Copying the logs about 0.71 s Inferred, not traced directly

Change 6: poll every 0.2 s. _wait_for_persisted_task_logs used time.sleep(1), and now uses _PERSISTED_LOG_POLL_SECONDS = 0.2. It still gives up after 30 s.

The cost is more reads of the jobs database, bounded by that 30 s limit, and only for a client following a job that finished without it seeing RUNNING, or for sky jobs logs on a task whose logs aren't saved yet.

Change 7: no separate lookup.

  • The combined head command prints the job's log directory as a fourth payload. It resolves the job ID once, so all the payloads describe the same job.
  • A new EndedJob(ended_at, log_dirs) tuple carries the end time and directory from the status check to the controller. It replaces the plain end time, and it's None until the job is terminal.
  • download_log_and_stream, download_and_stream_job_log and sync_down_logs gain an optional job_log_dirs. When it's set, sync_down_logs skips the lookup.
  • Renamed: get_job_status_and_ended_at → get_job_status_and_ended_job; pop_job_ended_at_seen_at_launch → pop_ended_job_seen_at_launch.

The lookup stays over gRPC (a cheap call), with a registered runtime, when the status check returned no directory, and on the cancelled-job and job-group download paths.

Interactions:

  • Changes 1 and 2 both shrink the time before GCS, so their gains overlap and shouldn't be added.
  • Change 5 moved time rather than removing all of it. G fell by 3.2 s while H rose by 1.4 s, because the client was already waiting on the same log save.
  • Changes 6 and 7 were measured together. I can't split the 1.7 s between them.

5. Failure handling #

Situation Behaviour
The pod watch fails Sleeps out the interval; the next poll decides.
A pod is deleted during the wait The watch ends early, and the poll handles it.
ray serve is used on a patched cluster Serve is imported on demand. --help, subcommands, an unknown subcommand's error and ray serve status were checked on Ray 2.56.1.
A skylet doesn't return timestamp_double The exact value is read through the head command.
A cluster has no jobs The log directory payload is empty, and the status check still succeeds.
The status check returns no end time or directory The controller falls back to try_to_get_job_end_time and the lookup in sync_down_logs.
The job ends just after its status is read The status isn't terminal, so the rest is dropped and the next check gets it.
The logs are never saved The client's wait gives up after 30 s and the tail ends with no warning, as before.
A launch is recovered What the earlier launch saw is cleared at the start of each wait, so it can't reach the new one.

6. Compatibility #

  • API, client and server: no API_VERSION bump.
  • Skylet: change 4 adds optional proto fields and bumps SKYLET_VERSION to 44, so existing clusters restart skylet to pick it up. Older clients keep reading the float. The consolidated doc's "everything is server-side or in the startup script" no longer holds.
  • Older cluster runtimes: the combined head command calls only functions the earlier commands call, and uses the same hasattr fallback as get_log_dirs_for_jobs. This wasn't run against an actual older runtime.
  • Custom images: they don't get the bytecode, as change 1 is in SkyPilot's Dockerfiles. Change 2 applies wherever the Ray patch applies.
  • sync_down_logs: the new argument is optional, so other callers are unaffected.

7. Risks #

  • Image size. The image is 160 MB larger, and no run paid for a cold pull of it.
  • The Ray patch needs maintaining with each Ray version, like the other patches.
  • More database reads while waiting for logs. On a server with many clients following short jobs at once, this could matter. It wasn't load tested.
  • A longer head command on every status check. The log directory lookup adds one small query to every monitor-loop check, not only the final one.
  • Trusting the tail's exit code. Change 5 treats it as SUCCEEDED before the controller records that. This is a critical code path (sky/jobs/) and should get close review.

8. Results #

All runs are on kind-skypilot, one kind node on 12 host cores, 6 nodes, consolidation mode. Each A/B has 8 measured runs per arm. Medians.

8.1 ej-prj-3-job2, why it was dropped #

ej-prj-3-job1 → ej-prj-3-job2, sky jobs launch, published image: client total 49.1 → 49.6 s (p = 0.93). The likely reason is a uv lock: the dry run holds the venv's lock while waiting on PyPI, so the wheel install still waits for it. This was reproduced in a throwaway container, but not observed inside a slow launch (precompile_runtime_bytecode_design.md).

Setup stalls remain. setup_runtime_on_cluster still reached 8.3 s and 11.6 s in the latest A/B.

8.5 Tests #

  • Unit tests on ej-prj-i2-6: 11,011 passed and 5 failed, excluding test_adaptor.py, which hangs here and on master. The 5 failures are in code these changes don't touch and pass when run alone.
  • Intermittent: test_checks_status_every_gap_otherwise failed twice during development (9213 sleeps instead of 15), then 0 of 25 on both ej-prj-i2-5 and ej-prj-i2-6. Cause not found.
  • mypy: only the 2 fetch_nebius.py errors, which also appear on master, so format.sh exits 1.
  • Real launches: change 5 had one launch each for a job that succeeds, fails (exit 3), is still running when its launch returns, and runs with gRPC on. The ej-prj-i2-6 code had 10 benchmark launches (warm-ups included) and 1 consolidation-mode check, all succeeding, plus 1 launch through a separate controller pod.

Not tested:

  • No smoke tests are recorded for any change in this doc. The consolidated doc's §7.5 ran against ej-prj-3-job1.
  • Change 7's failed-job path has no unit test and no launch.
  • Change 7 hasn't run with pool jobs or against an older cluster runtime.
  • Change 3's pod deletion during the wait is covered only by unit tests.
  • Change 4's new client with an older skylet is covered only by mocks.
  • The GPU image hasn't been built.

9. Remaining work, by expected gain #

Gains are for a 6-node sky jobs launch on kind. Times come from the ej-prj-i2-5 wait trace, so they're upper limits, and estimates where marked.

  1. Explain the bimodal phases A and C (about 6 s, §8.4). It's the largest unexplained time left.
  2. Publish the bytecode image and use IfNotPresent for the default image. Without these, users don't get the numbers here.
  3. Run the scheduler without a new Python process (1.55 s in phase B).
  4. Skip is_definitely_autostopping after the controller's own launch (about 2.0 s across E and F).
  5. Merge the head commands around submission: set_autostop 1.56 s, _add_job 1.56 s, queue job 1.58 s. gRPC by default would address the same cost.
  6. Fix the setup stalls: run the dry run only if the offline install fails, so a pod on SkyPilot's images never contacts PyPI (precompile_runtime_bytecode_design.md). Stalls add up to about 10 s.
  7. Shrink the client's own time. About 1.4 s remains between "Managed job finished" and exit.

A separate UX issue: in 10 of 11 traced runs the client never tailed the job, so a short job's logs appear in one burst after SUCCEEDED, not as they're written. Tailing the cluster directly when the logs aren't saved yet would fix that.

10. Reproducing #

sky jobs launch A/B, from the repo root with no other launches on the context. It restarts the API server with --deploy and switches the checkout, then restores both. It refuses uncommitted changes to tracked files.

python ej/reproduce_benchmarks.py jobs-ab --nodes 6 \
    --base ej-prj-i2-5 --candidate ej-prj-i2-6 \
    --base-task ej/task_bytecode.yaml \
    --candidate-task ej/task_bytecode.yaml \
    --blocks 4 --runs 4 --warmup 1

sky launch A/B, which needs no restart of your server:

python tests/kubernetes/launching_benchmarks/bench_launch_latency.py run \
    --baseline-ref <ref> --candidate-ref <ref> --context kind-skypilot \
    --task ej/task_published_ifnotpresent.yaml \
    --candidate-task ej/task_bytecode.yaml --runs 8 --warmup 1

If you start the server by hand, use sky api start --deploy. Plain sky api start turns consolidation mode off, and the next sky jobs launch creates a separate controller pod.
