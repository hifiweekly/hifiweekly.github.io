ej-prj-i2-2: [Jobs] Keep job timestamps exact over gRPC #

Commit: a84ddc783. Stacked on ej-prj-3-job1.

Summary #

  • Problem:
    • GetJobSubmittedTimestamp and GetJobEndedTimestamp return the time in a protobuf float, which can hold a current Unix time only to the nearest 128 s.
    • With SKYPILOT_ENABLE_GRPC on, a managed job's start and end times were off by up to about a minute, and a short job's duration was recorded as 0 s.
  • Fix:
    • Add optional double timestamp_double to both responses. A float can't be widened in place without breaking the wire format.
    • Keep setting the float, so older clients still work.
    • When a skylet doesn't set the new field, read the exact value through the existing head command instead of accepting the rounded one.
    • Bump SKYLET_VERSION to 44, so existing clusters pick this up.
  • Not a speedup: gRPC is off by default, so launch times don't change.

Files: sky/schemas/proto/jobsv1.proto and the generated files, sky/skylet/services.py, sky/skylet/constants.py, sky/jobs/utils.py, and a new test file.

ej-prj-i2-3: [Kubernetes] Start Ray and notice running pods sooner #

Commits: cab8b302a, 0038650ac, 16738238e. Stacked on ej-prj-i2-2.

Summary #

  • Precompile runtime bytecode in the k8s images (cab8b302a).
    • uv doesn't compile bytecode by default, so every pod compiled Ray and its dependencies on first import, before GCS started, which delayed every worker.
    • Add --compile-bytecode to the runtime install in Dockerfile_k8s and Dockerfile_k8s_gpu. The image grows from 1.67 GB to 1.83 GB.
    • This takes effect once the image is rebuilt and published.
  • Don't import Ray Serve in ray start (0038650ac).
    • ray start imported ray.serve.scripts only to register the ray serve command, which pulls in pandas and FastAPI on every pod.
    • A patch to Ray's scripts.py registers that command lazily, so Serve is imported only when ray serve is used.
    • apply_patches.py imported each module to find its file, which would have imported Serve to patch the file that avoids it. It now uses find_spec, which doesn't run the module.
  • Watch pods between polls (16738238e).
    • _wait_for_pods_to_run slept 1 s between polls, so a launch noticed its last pod about 0.5 s late on average.
    • A watch now ends the wait early when every waiting pod is running or a pod is going away. The poll that follows still makes every decision, and any watch failure falls back to sleeping out the interval.

Files: Dockerfile_k8s, Dockerfile_k8s_gpu, sky/skylet/ray_patches/, sky/provision/kubernetes/instance.py, and tests.

ej-prj-i2-4: [Jobs] Get a finished job's end time with its status #

Commit: b848c9c1e. Stacked on ej-prj-i2-3.

Before opening a PR: this commit's message says the client "still waits for its own log tail", which is wrong. Use the reworded copy on ej-prj-i2-5 (7db718aa0), or the wording below.

Summary #

  • Problem: after a managed job ended, the controller ran two commands on the head node (status, then end time), and the log follower ran its own status check. Without gRPC, each is a kubectl exec or SSH round trip of a second or more.
  • Fix:
    • The combined head command now also returns the end time.
    • A launch that saw the job succeed hands its status and end time to the monitor loop, which then needs no head command.
    • The monitor loop's status check also returns the end time, so a finished job doesn't fetch it separately. With gRPC or a runtime, it still does.
    • The follower trusts a tail exit code of SUCCEEDED, and reads the recorded status every 0.2 s instead of every 1 s until the controller writes it.
  • Compatibility: the generated code only calls functions older cluster runtimes already have.
  • Side effect: the wait after SUCCEEDED grows, because the controller saves the logs after SUCCEEDED and the client now reaches that wait sooner. The total still improves slightly.

Files: sky/jobs/controller.py, sky/jobs/recovery_strategy.py, sky/jobs/utils.py, sky/skylet/job_lib.py, and tests.
