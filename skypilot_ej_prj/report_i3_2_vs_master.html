Launch latency report: ej-prj-i3-2 vs. master #

Consolidates sky-launch/summary.md and jobs/report.md from bench_results/20261103-i3-2-vs-master-no-tips/.

Summary #

ej-prj-i3-2 cuts sky launch by 41% and sky jobs launch by 54% against master, with no speedup settings on either side. All 16 measured runs of each benchmark succeeded, and every branch run beat every master run.

Benchmark (median, with range) Master ej-prj-i3-2 Change p
sky launch wall time 46.70 s (41.5–56.1) 27.57 s (24.8–33.2) −19.13 s (−41%) 0.0002
sky jobs launch client total 74.33 s (72.3–81.7) 34.17 s (31.8–36.0) −40.16 s (−54%) 0.0002

These gaps include the bytecode image, which isn't published. They measure the whole branch and that image together, so users wouldn't see them today.

The benchmark's own checks all passed, and its verdict is VALID:

  • Each build ran its own commit, seen in the provision logs as 796c5bcc8041 and d771518f11d2.
  • All launches succeeded and ran on every rank.
  • No candidate launch fell back to restarting Ray.
  • The candidate never ran the old polling loop.
  • The primary metric, runtime installed → cluster launched, was lower with p < 0.05.

How to read this #

  • The storage check reuse shows up in phase A of sky jobs launch. All 8 measured branch runs were 1.8–2.3 s, and none hit an expired record. Launches were about 40 s apart, which is the best case: launches over 10 minutes apart get no saving.
  • That reuse is only part of the gap. A separate A/B of the patch alone measured 41.31 → 37.06 s (p = 0.013), with phase A at 6.85 → 2.20 s. The rest comes from the earlier ej-prj-i2-* branches and the bytecode image.
  • sky launch doesn't appear to benefit from the reuse. From the code, it reaches that check only for tasks with storage mounts (sky/task.py:1690), and this task has none.
  • Phase C doesn't improve. Its aws configure list call is a separate path from the storage check. aws.remote_identity: NO_UPLOAD removes it, or it costs less if aws isn't on the server's PATH.
  • The two benchmarks' environments differ. The sky launch venvs have no AWS libraries, so their cloud checks stop earlier than on the main server. Don't compare runtime or wall time directly between them.

Open questions #

  • File mounts are slower on the branch, for a reason not yet found: 1.05 s vs 2.33 s, with ranges 1.0–1.8 s and 1.4–3.1 s. The ej-prj-i3-1 comparison showed the same direction (1.76 s vs 2.26 s). No significance test was run on this stage.
  • Skylet start on its own is also slower on the branch: 1.60 s vs 2.68 s. It runs alongside the Ray wait, so it doesn't set phase D's length, and the cause hasn't been investigated.

Not covered #

  • ej-prj-i3-1's rsync change: this branch doesn't include it.
  • The patch's 10-minute limit at other launch rates: only launches about 40 s apart were tested.
  • Current master: origin/master was 2 commits ahead of 796c5bcc8 at last check.
