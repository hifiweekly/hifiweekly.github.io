ej-prj-i4-1: [Core] Poll for the head node every 0.2 s when a worker starts Ray #

Commit: 925abd467. Stacked on ej-prj-i3-2.

Summary #

  • Problem: a worker's ray start waits for the head's node record in GCS, and Ray's get_all_node_info_until_retrieved sleeps 2 s between checks (ray/_private/utils.py). A worker that checks just before the head registers waits up to 2 s more than it needs to.
  • Fix: a new Ray patch, utils.py.patch, sleeps 0.2 s and makes 10x as many attempts, so Ray still gives up after the same time.
    • It's registered in apply_patches._PATCHES, so it's applied with the other Ray patches when a pod starts.
    • utils.py.diff keeps the readable diff against Ray 2.56.1, as for the other patches.

Files: sky/skylet/ray_patches/apply_patches.py, sky/skylet/ray_patches/utils.py.patch, sky/skylet/ray_patches/utils.py.diff.

ej-prj-i4-2 / ej-prj-i4-4: [Core] Start skylet without importing sky #

Commit: d6fa30e94 on ej-prj-i4-4, stacked on ej-prj-i4-3. The same change is afd94a698 on ej-prj-i4-2, which has an 81-character comment line that d6fa30e94 fixes.

Before opening a PR: commit the mypy fix. constants.py re-exports SKYPILOT_ENV_VAR_PREFIX from launch_constants.py, and mypy can't infer its type through the import cycle, which gives 3 errors in sky/skypilot_config.py. Annotating the re-export (SKYPILOT_ENV_VAR_PREFIX: str = ...) fixes it, and is in the working tree.

Summary #

  • Problem:
    • start_skylet_on_head_node runs python -m sky.skylet.attempt_skylet.
    • -m runs sky/__init__.py first, which imports most of SkyPilot (about 2,170 modules), so a script that does a few milliseconds of work took 2–3 s.
  • Fix:
    • New sky/skylet/launch_constants.py holds the constants attempt_skylet.py needs. It imports nothing from sky, and constants.py re-exports it, so other code is unchanged.
    • attempt_skylet.py loads launch_constants.py by path. It has its own small copies of get_runtime_dir_path and find_free_port.
    • MAYBE_SKYLET_RESTART_CMD runs the script by path with runpy.run_path, found through importlib.util.find_spec('sky'), which doesn't import the package.
    • A cluster with an older wheel runs its older attempt_skylet.py the same way.
  • Not a launch speedup by itself: skylet starts alongside the Ray wait, which took longer, so the launch waited for Ray instead. It counts once Ray starts faster, as with the dashboard PR below.

Files: sky/skylet/launch_constants.py (new), sky/skylet/attempt_skylet.py, sky/skylet/constants.py, sky/provision/instance_setup.py, sky/utils/debug_utils.py (a docstring), and tests/unit_tests/test_sky/skylet/test_attempt_skylet.py.

ej-prj-i4-3: [Kubernetes] Install the SkyPilot wheel without the network when possible #

Commit: 8bfc6e4c6. Stacked on ej-prj-i4-1.

Summary #

  • Problem:
    • Runtime setup waits for every pod. Each pod ran a uv pip install --dry-run that sends over 100 requests to PyPI, even when the image already has everything.
    • One request hanging on one pod (uv's connect timeout is 10 s) delayed the launch by about 5–10 s, in a third or more of launches in some sessions. DNS settings didn't fix it.
  • Fix:
    • sky/skylet/constants.py: install the wheel with uv pip install --offline first. If what's installed and cached can't satisfy it, fall back to the normal install.
    • kubernetes-ray.yml.j2: skip the dry run, which only warms uv's cache, when the image already has a populated cache (~/.cache/uv/archive-v0). Images without a cache behave as before.
  • Shared with other clouds: the wheel command is used on every cloud, but it has only run on kind, not on real VMs.

Files: sky/skylet/constants.py, sky/templates/kubernetes-ray.yml.j2, and a new test file.

ej-prj-i4-5 (1 of 2): [Core] Don't start the Ray dashboard on SkyPilot clusters #

Commit: 1266cccd2. Stacked on ej-prj-i4-4.

Before opening a PR, decide whether users need a way to keep the dashboard. As written, every SkyPilot cluster loses it, and there's no opt-out. See "What users lose".

Summary #

  • Problem:
    • SkyPilot doesn't use the Ray dashboard, but it delays every node's raylet.
    • On the head, ray start polls every 0.1 s until the dashboard publishes its address, which waits for the dashboard to load its modules. Only then does it start the raylet.
    • On every node, the raylet waits for the dashboard agent, which imports every module under ray.dashboard.modules.
    • --include-dashboard=false doesn't avoid this: Ray still starts a dashboard process for usage stats, and the wait remains. Tested alone, it saved about 1 s in Ray and nothing in the launch.
  • Fix: SKYPILOT_RAY_NO_DASHBOARD=1 on SkyPilot's head and worker ray start commands, read by two new Ray patches.
    • services.py.patch: start_api_server returns at once without starting the dashboard, and the dashboard agent starts with --minimal.
    • agent.py.patch: the agent loads no dashboard modules.

Files: sky/provision/instance_setup.py, sky/skylet/ray_patches/apply_patches.py, and services.py and agent.py patches (each .patch and .diff).

What users lose #

  • Ray's dashboard UI. docs/source/reference/architecture/internals.rst:63 lists its port, 8266, and needs updating.
  • Ray's metrics export.
  • Ray's job and state APIs: ray job, ray list and ray summary on a cluster. SkyPilot doesn't use them, as far as found.

ej-prj-i4-5 (2 of 2): [Core] Retry Ray's local socket connects every 0.2 s #

Commit: fa974f21e. Stacked on 1266cccd2.

Summary #

  • Problem:
    • Each raylet starts its plasma store on a thread, gives it 500 µs, then connects to the store's socket (object_manager.cc:57, :143).
    • The store maps 500 MB of shared memory before it binds the socket, so the first connect often fails.
    • Ray then sleeps raylet_client_connect_timeout_milliseconds, 1000 ms by default, before retrying (client_connection.cc:87).
    • In 6 traced launches, this hit 13 of 36 raylets and was always the last worker to register. With the dashboard, it was hidden behind the agent wait.
  • Fix: set RAY_raylet_client_connect_timeout_milliseconds=200 and RAY_raylet_client_num_connect_attempts=50 on SkyPilot's head and worker ray start commands, through one constant, _RAY_CONNECT_RETRY_ENV.
    • Ray reads every RAY_CONFIG value from RAY_<name> (ray_config.h:74), and the raylet's worker processes inherit both.
    • The same pair sets how long Ray workers retry connecting to the raylet. 50 attempts keeps Ray's default 10 s before giving up.
    • Ray's own Docker tests set the same pair, to 100 ms (python/ray/tests/conftest_docker.py:156).

Files: sky/provision/instance_setup.py, and a new test file.

Tested #

  • [x] Code formatting: yapf --diff and isort --check are clean on the changed files. Pylint on the changed sky/ files rates 10.00/10. mypy has no errors beyond master's 2 in fetch_nebius.py.
