Launch latency: 4-node ej/job.yaml on kind (5 runs) #

  • Branch: ej-prj-bonus (6db5eba63). It contains idea #1 (pods start Ray first), idea #2 (one blocking Ray wait), idea #3 (skylet started during the wait), and the fail-fast change for deleted pods.

  • Task: ej/job.yaml with num_nodes: 4 (1 CPU, 1 GB each), on kind-skypilot (one kind node, 12 host cores).

  • Method: 5 launches in a row (ej-n4r1–ej-n4r5). Each was torn down before the next one started. The API server ran with SKYPILOT_TIMELINE_FILE_PATH. For each run I collected:

    • the server's timeline spans;
    • the provision log;
    • the client's start and end times;
    • the rank start times the task prints;
    • inside each pod: the container start, the time the bootstrap step-2 marker and the wheel were written, and the first log lines of Ray's GCS and raylets.

    The scripts are run_one.sh and analyze_runs.py in the session scratchpad.

2. Where a steady launch spends ~34 s #

client log tail       2.7  ▇▇▇
                     ----
                     33.9

Three things stand out:

  1. Ray is the critical path in every steady run. Runtime setup finishes 7.4–8.5 s before the last worker's raylet starts, so the provisioner then waits ~10 s for Ray. Skylet (3.8 s) is fully hidden behind that wait. From a pod's container start:

    • ~3.5 s to the step-2 marker (Ray installed and patched, uv cache warmed);
    • ~3.8 s more until the head's GCS starts logging. That includes ray stop on a pod that has never run Ray, and the start of ray start --head;
    • ~4.0 s more until the head's raylet;
    • workers can only start Ray once the GCS port is up, and their raylets come ~5.5 s after the GCS.

    So the head takes ~11 s from container start to its raylet, and the whole cluster ~13 s until every node has joined.

  2. After "Cluster launched", ~12.3 s go to the job, with almost no variance:

    • 3.4 s submitting it with two kubectl exec calls (gRPC is off by default);
    • ~3.7 s for the driver to connect to Ray, create the STRICT_SPREAD placement group, and start a cold Ray worker for rank 0;
    • 1.8 s until the last rank starts;
    • ~2.7 s until the client's log tail notices the job finished.

    That's more than pod creation, file mounts and runtime setup put together.

  3. The fixed costs are tight: write_cluster_config 2.7 s and pods 4.4 s (each pod still checks the registry for its image) are the same in every run.

3. The outlier (run 1: 51.0 s, +17 s) #

  • worker1 took 25.3 s to write its step-2 marker; the other pods took ~4 s. Its raylet also came late (19.8 s after the head's GCS). Runtime setup waits for every pod's marker, so it took 20.6 s, and that delay accounts for the extra ~17 s.
  • Only the dry run, which warms uv's cache with a PyPI resolve, depends on the network in that step. That makes it the likely cause, as in the 6-node runs.
  • It was also the first launch after the API server restarted. That explains the 3.8 s CLI-to-launch time, but not the slow pod: pod bootstrap doesn't depend on the server.
  • 4 nodes compared with 6 nodes: a slow pod showed up in 1 of 5 runs here, against 3 of 4 runs with 6 nodes. Fewer pods starting at once means less contention for CPU and network, so it happens less often, but it still happens.

4. What else could be done, for this workload #

# Idea Phase it shortens Expected gain (steady)
1 Start the head's Ray sooner: skip ray stop on a freshly booted pod; bake the setuptools<70 / click pins and the Ray patches into the image; turn off the Ray dashboard if SkyPilot doesn't use it Ray wait (critical path, 10.4 s) 2–4 s. Every second on the head is a second for the workers too, since they wait for its GCS port
2 Submit the job over gRPC (SKYPILOT_ENABLE_GRPC, or make it the default), or merge add_job and queue_job into one exec Job submit (3.4 s) ~3 s, every launch and every sky exec
3 Start the job's ranks sooner: prestart a Python Ray worker on each node during setup; look at the driver's ray.init and the STRICT_SPREAD placement group Driver + placement group (3.7 s) + rank spread (1.8 s) 2–4 s
4 Shorten the client's log-tail lag once the job ends (poll more often, or end the stream on job completion) Client tail (2.7 s) ~2 s you'd notice
5 Install the wheel offline first and drop the dry run Rare slow pod (+17 s in 1 of 5 runs) Removes the tail risk and the per-launch PyPI dependency
6 Profile write_cluster_config; pin the image by digest with IfNotPresent 2.7 s + 4.4 s 1–3 s

Rough effect if 1–4 land: ~9–13 s off a ~34 s launch, which puts a 4-node launch on kind at around 21–25 s. Idea 5 keeps the occasional ~50 s launch from happening.

Interaction with skylet. Once idea 1 shortens the Ray wait to about the skylet start (3.8 s), skylet becomes the bottleneck. Starting skylet earlier (from the pod's own bootstrap, or in the same exec as runtime setup) is the follow-up that keeps the gain.

5. Caveats #

  • One kind node runs all 4 pods, so they compete for CPU and network. On a real multi-node cluster, Ray start and the dry run should be faster and less noisy, and pod creation includes scheduling and image pulls on separate nodes. Confirm the ranking there before investing in ideas 1 and 6.
  • 5 runs (4 steady) is enough to rank the phases, because the steady spreads are small. It's not enough to estimate how often the slow-pod tail happens.

6. Experiment: job submission over gRPC (idea #2) #

Setup: same branch, task and method as above. The only change is SKYPILOT_ENABLE_GRPC=1, set on the API server (and the client). I ran one untimed warm-up launch after the server restart, then 3 measured runs (ej-g1–ej-g3).

gRPC was really used. The trace of every gRPC run has no run_on_head calls (each baseline run has 2: add_job and queue_job). Neither the request logs nor the server log mention gRPC failed or falling back to SSH.

What it shows:

  • Job submission drops from ~3.7 s to ~0.5 s. The two kubectl exec + Python round trips become two gRPC calls to skylet. g1 took 1.4 s, probably the cost of opening the skylet tunnel to a new cluster for the first time. Every launch is a new cluster, so expect that cost on some launches.
  • The time from "Cluster launched" until the client returns falls by ~3.5 s, from 11.7 to 8.2 s. A little of that (~0.3 s) comes after the job, presumably because the client's job-status checks also go over gRPC.
  • Client totals are noisy for an unrelated reason. g1 and g2 hit the slow-pod problem (one pod took 11–15 s to finish its bootstrap, so runtime setup took 10–11 s). That happens before any job is submitted, so gRPC can't affect it. g3 had no slow pod and finished in 29.9 s, against 33.4–35.0 s for the steady baseline runs: about −4 s, which matches the per-phase numbers.
  • The slow pod appeared in 2 of 3 runs here, against 1 of 5 in the baseline. With so few runs that's noise, but it confirms that slow pods (idea #5: install offline, drop the dry run) are now the main source of variance.

Conclusion: turning on gRPC saves ~3–3.5 s on every launch (and on every sky exec, which uses the same path), with no fallbacks seen. Before making it the default, find out why SKYPILOT_ENABLE_GRPC is off by default (search git history and issues), and test clusters whose skylet tunnel can't be reached, to check that the fallback to SSH still works.
