Inside attention, the gpt-oss version

gpt-oss's attention has the same job and the same name as Gemma 3's kernel, but it is a different kernel. Heads are 64 wide, so a block is only 4 warps and each lane owns 2 dims. The softmax is computed in two exact passes instead of online: the first pass scores every visible key and parks the scores in shared memory, the second turns them into weights against the true maximum and sums the values. Each head also has a learned sink logit, which competes in the softmax but brings no value vector, so a head can put part of its attention on nothing. Even layers see only the last 128 positions, read from a ring of cache slots (256 with the default 128-token prompt chunk).

out = Σj=lo…p eq·kj/8 − m · vj / ( Σj eq·kj/8 − m + esinkh − m )   // m = max(scores, sink); lo = p − 127 on window layers

Four warps, one key each, two passes

Each column of the grid is one loop iteration and each row one warp: warp w takes keys w, w + 4, w + 8 … of the visible range, one key per iteration, so relative key index = 4·iteration + warp. Why it is built this way

    

      

        
Two passes instead of an online softmax

        
Gemma 3's kernel keeps a running maximum and rescales its 256-float accumulator whenever the maximum grows. Here a score costs only 4 bytes of shared memory, and a window layer has at most 128 visible keys (512 bytes), so it is cheaper to store every score, take the exact maximum once, and exponentiate each score exactly once against it. K is still read once (pass 1) and V once (pass 2), so the memory traffic is the same as a single pass; nothing is ever rescaled.

        
The dynamic shared allocation is 4 bytes per key, sized by the host from the longest key range in the launch: min(pos0 + T, 128) on window layers, pos0 + T on full ones.

      

      

        
The sink: attention to nothing

        
Every head has one learned logit, attn_sinks[h]. It enters the maximum and the denominator like an extra key, but has no value vector, so the weights of the real keys sum to less than 1. A head that finds nothing relevant can send most of its weight to the sink and output a vector near zero, instead of being forced to average whatever is in the window. In the kernel it costs one load, one max and one extra exponential in the final denominator.

        
The panel where the weight goes shows the split for the selected head; with the generated data here, heads 10 and 11 send most of their weight to the sink, and most others only a few percent.

      

      

        
Small heads: 4 warps, 2 dims per lane

        
A 64-dim f16 key is 128 bytes, one 4-byte load per lane, and one dot product is two multiply-adds per lane plus a 5-round butterfly. Four warps keep four keys in flight per block, and 64 q heads × tokens blocks fill the GPU. Eight q heads share each kv head (64 / 8), so the other seven blocks of a group usually find its K and V rows in L2.

      

      

        
A ring of 256 slots

        
Window layers keep the last 128 positions plus one prompt chunk in a ring: 128 + 128 = 256 slots with the default chunk (the ring is sliding_window + batch), and key j lives in slot j % 256. The kernel computes the slot of its first key with one rem, then steps it by 4 and subtracts 256 when it passes the end, so the loop has no division. Full layers have one slot per position.

        
The final merge needs 1 KB of shared memory for the 4 partial accumulators; threads 0–63 each finish one output dim, and threads 64–127 leave.
