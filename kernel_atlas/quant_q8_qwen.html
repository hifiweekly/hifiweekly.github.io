Inside quant_q8, the Qwen version

Every Qwen 3.5 weight product is an integer dot product (dp4a, or int8 mma in prefill), so each activation vector is first turned into Q8 blocks: 32 consecutive values share one float scale d and each becomes round(x / d), between −127 and 127. One warp handles one block, one lane per value.

It starts like the gpt-oss / Gemma 3 kernel but writes one more number per block: d · Σq, the block's sum in the scale of x. Qwen's Q4_1 and Q5_K weights carry an offset per block (w = dw·n + m), and that offset multiplies the plain sum of the activations. With d · Σq stored here, mv_q4_1 and mv_q5_k pay one multiply-add per block for it. A second butterfly, on integers, makes the sum. The in-place float mode is gone: the prefill GEMM reads int8 too.

d = maxj<32 |xj| / 127    qj = round(xj · (1/d))    ds = { d, d · Σj qj }

Where it runs

Before every weight product: three launches per DeltaNet layer, three per attention layer, plus one before the output head. Prefill runs the same launches on T tokens at once. Selecting a row sets the data and grid on the rest of the page.

What d · Σq is for

      
A Q4_1 weight block stores 32 nibbles nj, a scale dw and an offset m, so wj = dw·nj + m. Its dot product with this activation block splits in two:

    

    

      
Σj wj · qjd = dw · d · Σ njqj  +  m · (d · Σ qj)   // dp4a gives the first sum; quant_q8 already stored the second

Why it is built this way

    

      

        
Paying for the offset once per activation block

        
Without the stored sum, every weight row would have to add up the 32 activations of every block again: 4096 columns are 128 blocks, so a 12,288-row product would repeat the same 128 sums 12,288 times. Computing them here costs five integer shuffles per block, once. The sum is exact: 32 values of at most 127 fit easily in 32 bits, and add.s32 has no rounding.

        
Storing d · Σq rather than Σq saves the reader a convert and a multiply, and storing it next to d as a float2 means one 8-byte load gives the reader both numbers. Q5_K uses the same sum for its per-sub-block minimum, and Q8_0 weights (β ‖ α, and every matrix of the Q8_0 file) simply ignore the second float.

      

      

        
No in-place mode, and the same rounding as before

        
gpt-oss and Gemma 3 run their prefill GEMMs on floats, so their quant_q8 can overwrite x with q · d instead. Qwen's gemm_q multiplies int8 tiles with tensor-core mma.m16n8k32, so prefill wants exactly the decode output: the null-pointer branch was removed.

        
The scale and rounding are unchanged: d = amax / 127 with an IEEE division, one reciprocal, cvt.rni (to nearest, ties to even), and an all-zero block gives d = 0 and q = 0. The engine's self-test checks q, d and d · Σq against a CPU copy bit for bit.
