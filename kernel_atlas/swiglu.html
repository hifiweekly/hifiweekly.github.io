Inside swiglu

Every Qwen 3.5 layer ends with a SwiGLU feed-forward. One stacked Q4_1 matrix produces the gate and up projections side by side, 2 × 12,288 values per token; swiglu applies SiLU to the gate half and multiplies by the up half, giving the 12,288 inputs of the down projection. SiLU is x · σ(x), and the sigmoid costs one base-2 exponential and one division. It is geglu with a different activation: same indexing, half the arithmetic.

out[t][j] = SiLU(g) · u    SiLU(g) = g / (1 + e−g)   // gu[t] = [g: n | u: n], n = 12,288; e^−g computed as 2^(−g · log₂e)

One element, instruction by instruction

Pick g and u and step through one thread's instructions. The formula g / (1 + e−g) needs no special cases: for very negative g, e−g overflows to ∞ and the division gives −0; for very positive g, e−g = 0 and the result is g itself.

Finding g and u from a flat index

      
The grid-stride loop runs over i = 0 … tokens·n − 1, the output elements. Each token's input row holds 2n values, so the thread divides once to find its token, t = i / n; the gate sits at gu[i + t·n] and the up value n floats later. Why it is built this way

    

      

        
A separate launch, on purpose

        
SiLU could be applied in the epilogue of the gate ‖ up product, but the down projection needs its input as int8 blocks, so quant_q8 runs in between anyway. Keeping swiglu separate leaves the matrix kernels format-generic. Its cost is small: per layer and decode token it reads 96 KB and writes 48 KB; over the 32 layers that is about 1/1000 of what the matrix products read.

      

      

        
Matching llama.cpp

        
ggml computes silu(x) = x / (1 + expf(−x)) and multiplies by the up value. The kernel uses the same expression; the only difference is ex2.approx for the exponential, a relative error near 2⁻²². For a decode step the output feeds an int8 quantization with steps of 1/127 of the block maximum, far coarser.
