EmbeddingGemma 2 · emb2.ptx · element-wise, grid-stride, in place

Inside gelu_mul

EmbeddingGemma 2 gives every layer a second input besides the residual stream: 512 values per token, computed once from the token's embedding before the first layer (ple, 24 slices of 512 per token). After its feed-forward, each layer projects the stream to a 512-value gate, and gelu_mul multiplies GELU(gate) by the layer's slice of ple. The result is projected back and added to the stream by norm_add. The GELU arithmetic is geglu's; what is new is where the second operand lives.

g[t][i] = GELU(g[t][i]) · ple[t][l][i]   // ple row stride 24 · 512 = 12,288 floats; the kernel gets ple + l·512 and that stride

Reading one layer's slice of a [T][24][512] buffer

The per-layer inputs of all 24 layers sit together, token by token: row t holds layer 0's 512 values, then layer 1's, and so on. The kernel is told where layer l's slice of token 0 starts (ple + l·512) and the row stride (12,288 floats), so the same code serves every layer without copying the slice out. The gate buffer g is a plain [T][512] array and is overwritten in place.

Why it is built this way

    

      

        
A strided view instead of a copy

        
The 24 per-layer inputs are computed by one big product (12,288 × 512) before layer 0, so they come out interleaved by token. Re-packing each layer's slice into its own buffer would cost a copy per layer; passing a base pointer and a row stride costs one mad per element. Within a token the 512 values of a slice are contiguous, so a warp still reads 128 contiguous bytes.

      

      

        
In place, one launch

        
The gate g is consumed by exactly one product (proj), so the result can overwrite it: no extra buffer. GELU and the multiply in one element-wise launch read two floats and write one; as two launches they would read three and write two. For 512 values per token this kernel moves about 6 KB per token per layer, a small fraction of the layer's time.
