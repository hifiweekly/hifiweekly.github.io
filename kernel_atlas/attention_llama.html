Llama 3.1 · llama31.ptx · one block per query head per token, 128-dim heads

Inside attention (Llama)

For one query head of one token, this kernel scores every cached key from position 0 to the token's own, turns the scores into softmax weights and sums the value vectors with them. It is Gemma 3's attention cut down to Llama's shape: heads of 128 dims instead of 256, so each lane owns 4 dims instead of 8; 32 query heads sharing 8 key/value heads; no sliding window and no output gate. The scores are never stored: each of the 8 warps walks its share of the keys with an online softmax, and the 8 partial results are merged at the end.

out = Σj=0…p softmaxj(q · kj / √128) · vj   // kv head = q head / 4; scores kept in log₂ units

Eight warps, two keys at a time

Each column of the grid below is one loop step. Each row is a key slot within the step: rows 0–7 are key i of warps 0–7, rows 8–15 are key i + 8 of the same warps. So warp w owns rows w and w + 8, and key = 16·step + row. Within a warp, lane l owns dims 4l to 4l + 3 of q, k, v and the accumulator. Choose a position and a q head; click a key to inspect it.

What changed from the 256-dim kernel

      
The loop structure, the online softmax and the merge are the Gemma 3 kernel's, line for line. Everything that depended on the head size, and the features Llama does not use, changed.

    

    

      

        

      

      

        
Half the block idles at the end

        
The final write gives one thread per output dimension. With 256 threads and 128 dims, threads 128–255 take part in the barrier and then branch to ret; the other half reads the 8 warps' accumulators for its dim from shared memory (stride 512 bytes, one row per warp) and divides by the common denominator. Keeping 8 warps matters more than the idle tail: they are what keeps 16 keys in flight per block while the loop runs.

        
Grouped-query sharing

        
q heads 4g … 4g + 3 all read kv head g. Their 4 blocks run at about the same time and read the same 512 bytes per key (256 of K, 256 of V), so 3 of the 4 reads hit in L2. Per decoded token a layer reads 4 KB of cache per position from DRAM: at 8,192 positions that is 32 MB per layer, about 1 GB per token over the 32 layers, against the 7.95 GB of weights.

      

    

  


  

    
Why it is built this way

    

      

        
Online softmax

        
Softmax needs the maximum score before it can exponentiate, which would mean two passes over the keys. Instead each warp keeps m (largest score so far), l (sum of 2s − m) and acc (sum of 2s − m·v). When a larger score arrives, the old l and acc are multiplied by 2m_old − m_new. The result is exact up to rounding, and the keys are read once. Scores are scaled by log₂e up front (folded into q), so every exponential is one ex2.approx.

      

      

        
Where it is slow

        
One block per (q head, token) gives a decode step only 32 blocks for 56 SMs, and each warp walks p / 8 keys in sequence. That is fine for chat-length contexts: at a few thousand positions attention is a few percent of a token's time. For prompts the 32 × T blocks fill the GPU, but every key is still processed on the CUDA cores, one dot product per warp; llama.cpp's flash-attention kernels use the tensor cores and are part of why its prompt speed is 2.2× higher.
