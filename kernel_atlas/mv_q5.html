Inside mv_q5

Gemma 3's feed-forward weights are two thirds of the model, so the engine stores them in Q5_0: 5-bit integers with one f16 scale per 32 values, 5.5 bits per weight. mv_q5 multiplies them by the token's activation, which quant_q8 has just turned into int8. It runs twice per layer in decode: once for the stacked gate ‖ up matrix and once for down. The interesting part is rebuilding each 5-bit weight from a nibble and a separately stored fifth bit, four at a time, without a loop.

y[r] = Σb d[r][b] · xd[b] · ( Σj<32 qj · xj − 16 · Σj<32 xj )   // weight = (q − 16) · d, q in 0…31

One lane, one Q5_0 block

A block is 16 bytes of nibbles (qs), a 32-bit word of fifth bits (qh) and an f16 scale (d), kept in three separate arrays. Step through how a lane rebuilds the 32 weights and takes the dot product with integer instructions only, until one float multiply-add at the end.

Why it is built this way

    

      

        
The −16 once per block, not per weight

        
Q5_0 stores q = w/d + 16, an unsigned 0…31. Subtracting 16 from every weight would cost 32 operations per block. Instead the kernel multiplies the unsigned q directly (dp4a.u32.s32: unsigned weights, signed activations) and corrects once: Σ(q − 16)·x = Σ q·x − 16·Σ x. The Σ x comes from eight more dp4a against 0x01010101, and the 16· is a shift.

        
Everything up to that point is exact integer arithmetic. The one rounding step per block is the final FMA with d · xd.

      

      

        
Stacked gate ‖ up, split arrays

        
Gemma's gate and up projections read the same input, so the engine stacks them into one 30,720 × 3840 matrix at load time: one launch, one pass over xq, and geglu reads both halves from gu. The down projection is a separate 3840 × 15,360 matrix.

        
In the GGUF a Q5_0 block is 22 contiguous bytes, which is not 16-byte aligned. The loader splits blocks into qs, qh and d arrays, so each lane reads its 16 nibble bytes with one aligned v4.u32 and a warp reads 512 consecutive bytes of qs per round.
