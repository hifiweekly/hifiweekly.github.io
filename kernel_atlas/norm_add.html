Inside norm_add

Gemma's sandwich norm puts an RMSNorm on every sub-block's output before it joins the residual stream. EmbeddingGemma 2 does that twice per layer after attention's add_rmsnorm: once for the feed-forward output and once for the per-layer-input branch, and the second time the whole stream is then multiplied by a learned scalar of that layer. norm_add is the post-norm and residual add with that scale, and without add_rmsnorm's third pass: the next consumer of x here is a matrix product on the raw stream (inp_gate) or a separate rmsnorm.

x = ( x + y · sy · w ) · scale   // sy = 1 / √(Σ y² / 512 + ε), ε = 1e-6

One row: 256 threads, 512 values, one reduction

Thread t owns elements t and t + 256. Pass 1 sums y², a warp butterfly and 8 partials in shared memory give the row's sum, and pass 2 updates x in place. Pick the call site; for the second one, pick the layer to use its real output scale.

Why it is built this way

    

      

        
Folding the layer scale into the add

        
llama.cpp writes the per-layer branch as three graph nodes: the post-norm, the residual add, and a multiply of the whole stream by layer_output_scale. The scale is one float per layer, so the engine reads it once at load time and passes it as a kernel argument; multiplying in the same pass that writes x costs one instruction and saves a full read and write of the stream. The feed-forward call site passes 1.0 and pays one multiply.

      

      

        
Why not reuse add_rmsnorm

        
add_rmsnorm always finishes with the pre-norm of the next sub-block (a second reduction and a third pass). Here the next step either reads the raw stream (the inp_gate product after the feed-forward) or comes after the scale (the next layer's rmsnorm), so that work would be thrown away. A kernel with one reduction and two passes is simpler than a flag.

        
With 512 values a row is two laps of 256 threads, so the block uses 8 warps and 8 of the 32 shared slots.
