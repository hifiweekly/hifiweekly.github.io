Inside mv_f32

Before the experts run, a small linear layer scores all 32 experts for the token. mv_f32 computes those 32 router logits from the normalized hidden state: a 32 × 2880 matrix in plain float32, times a vector, plus a bias. It is the simplest matrix kernel in the engine and a good baseline for the quantized ones: one warp per output row, each lane striding through the columns, a butterfly to finish.

logit[t][e] = Σc<2880 W[e][c] · xn[t][c] + b[e]   // W = ffn_gate_inp.weight, b = ffn_gate_inp.bias, e < 32

32 rows, 32 warps, 90 loads each

The grid is (4, tokens) blocks of 256 threads, so each token gets 32 warps, one per expert row. In every iteration of the loop a warp reads 32 consecutive floats of its row and of x: lane l takes columns l, l + 32, … l + 2848. Each cell below is one such 128-byte chunk. Why it is built this way

    

      

        
Why the router stays in float32

        
The router matrix is 32 × 2880 × 4 bytes = 360 KB per layer, 8.4 MB over 24 layers: next to the 10 GB of MXFP4 experts it costs nothing to keep exact. And its output is a decision, not a value: if quantization noise swaps the 4th and 5th expert, the token goes through a different expert altogether. llama.cpp keeps it in F32 as well, so the engine routes the same way.

      

      

        
A tiny launch

        
In decode the grid is just 4 blocks: 4 of the GPU's 56 SMs do the work and the rest idle for the microsecond or two it takes. Splitting the columns across more warps would need a second reduction across warps; the kernel instead keeps the plain one-warp-per-row shape, and in prefill the grid's y dimension (one slice per token) fills the GPU.

        
Weights use ld.global.nc, the read-only path; x uses a plain load. All 32 warps read the same x, so after the first warp it comes from cache.
