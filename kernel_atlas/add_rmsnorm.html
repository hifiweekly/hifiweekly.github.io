Gemma 3 · gemma3.ptx · one block per token, three passes

Inside add_rmsnorm

Gemma 3 normalizes twice around every sub-block: the attention and feed-forward outputs get their own RMSNorm before they are added to the residual stream, and the stream is normalized again before the next sub-block. add_rmsnorm does the post-norm, the residual add and the next pre-norm in one launch, so each layer ends its two halves with this kernel instead of three.

x += y · sy · w1    xn = x · sx · w2   // sv = 1 / √(Σ v² / n + ε), n = 3840, ε = 1e-6

One row: 1024 threads, 3840 values, two reductions

Thread t owns elements t, t + 1024, t + 2048 and, for t < 768, t + 3072. Each pass is a strided loop over those elements; a reduction (warp butterfly, 32 partials in shared memory, one barrier) sits between passes. Click a point on the plots to follow its thread.

Why it is built this way

    

      

        
What fusing saves

        
Done as three kernels (normalize y, add, normalize x), the row would make an extra round trip through memory for the normalized y and read x once more. Per token, in floats of the 3840-wide row:

        

        
The bigger saving is launches: two per layer instead of six, 192 fewer per token over 48 layers. At decode each launch moves only about 120 KB, so launch overhead is a large share of its time.

      

      

        
Reading back x without a second barrier

        
Pass 2 writes the new x and pass 3 reads it. That would normally need a barrier, but each thread reads back only the elements it wrote itself, so program order is enough. The barriers that do exist are the two around the reductions, where every thread needs every warp's partial sum.

        
Every thread adds the same 32 partials in the same order, so all threads get bit-identical scales without a broadcast. The two shared arrays (arn_red1, arn_red2) are separate so a fast warp writing its pass-2 partial cannot overwrite a pass-1 partial that a slow warp is still reading.
