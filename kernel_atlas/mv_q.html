Llama 3.1 · llama31.ptx · decode: one warp per row, any of 9 ggml formats

Inside mv_q

Every matrix of Llama 3.1 is multiplied by this kernel when a token is generated: the stacked q, k, v projection, the output projection, gate and up, down, and the 128,256-row output head. It is a plain one-warp-per-row matrix × vector product like mv_q8_0, with one difference: it does not know the weight format. A device function, unpack16, turns 16 weights of any of 9 ggml block formats into 16 int8 values, a scale for those 16 and an offset for their 32-value block. After that, every format is the same exact integer dot product. The Q8_0 Llama file needs only one of the 9 paths; a Q4_K_M or IQ4_XS file of the same model runs through this kernel too.

y[r] = Σb dₓ[b] · (s₀ Σj<16 qjxj + s₁ Σj≥16 qjxj) + m · dₓΣx + resid[r]   // weight = sh·q + m, q int8 from unpack16; activation = dₓ·x, x int8

Why it is built this way

    

      

        
One decoder, two kernels

        
The Unsloth file of Qwen 3.8 27B mixes eight formats, sometimes three within one stacked product. Writing a matrix-vector kernel and a GEMM per format would be 18 kernels that must agree bit for bit. Instead both mv_q and gemm_q call unpack16 (a PTX .func with six return registers, which ptxas inlines) and do the arithmetic on its output. A new format is one more branch in one function.

        
Half blocks of 16 are the unit because the K-quants Q3_K and Q6_K give every 16 values their own scale; formats with one scale per 32 return the same s twice. The offset m (Q4_1's min, Q4_K and Q5_K's −dmin·m) is constant over 32 values, so it costs one FMA with the activation block's dₓΣx, which quant_q8 stores next to dₓ.

      

      

        
What generality costs

        
The type is a kernel parameter, so every lane of every warp takes the same branch in unpack16: no divergence, just a chain of compare-and-branch at each call, 16 per lane per 4,096-column row. For Q8_0 the decode path is then the same loads as mv_q8_0 plus that dispatch. Llama 3.1 decodes at 55 tokens/s, reading 7.95 GB per token: 440 GB/s of the RTX 4070 SUPER's 504, within 2% of llama.cpp on the same file.

        
The cost shows instead in instruction count for the packed formats (IQ3_S does a grid lookup per 4 weights), and in the prompt GEMM, which decodes each weight once per 64 tokens instead of reading pre-decoded tiles.
