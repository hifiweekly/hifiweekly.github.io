Inside moe_sort

gpt-oss sends every token to 4 of its 32 experts. During prompt processing, the expert GEMM wants each expert's tokens side by side, so that expert's weights are read once for the whole chunk instead of once per token. moe_sort builds that grouping: a counting sort by expert id, done by one block with shared-memory atomics. It is a classic histogram → prefix sum → scatter, small enough to watch in full.

ids[p] = expert of pair p = (token t, slot j), p = 4t + j  →  list[offs[e] … offs[e+1]) = the pairs routed to expert e

24 tokens × 4 experts = 96 pairs

Colors mark the 32 experts. With 1024 threads and only 96 pairs, thread p handles pair p, so the strided loops run once. Step through the three phases; the last phase shows why the order inside a bucket is not fixed.

Why it is built this way

    

      

        
One block is enough

        
A prompt chunk has at most 128 tokens, so n ≤ 512 pairs and 32 counters. Everything fits in one block's shared memory, the atomics stay on-chip, and the only synchronization needed is bar.sync between phases. The prefix sum over 32 counters is done serially by thread 0: 32 additions are faster than organizing a parallel scan.

      

      

        
Why arbitrary order is fine

        
Atomics return slots in whatever order the hardware serves them, so two runs can list a bucket's pairs differently. The expert GEMM writes the result for pair p into row p of its output, and moe_combine later sums each token's 4 rows with their router weights. The position inside the bucket never reaches the math, so results stay deterministic.
