Gemma 3 · gemma3.ptx · one warp per head

Inside qk_norm_rope

Right after the Q/K/V projection, Gemma 3 normalizes every query and key head on its own (RMSNorm over 256 dimensions), rotates them by their token's position (rotary embedding, NeoX layout), and writes keys and values into the KV cache as f16. One 32-thread block handles one head of one token, so the whole head lives in a single warp's registers and never touches shared memory.

x' = RoPEpos( x / √(Σ x² / 256 + ε) · w )   // pair (i, i+128): [xi, xi+128] rotated by pos · θi

The grid: 32 heads per token

Each token's projection output holds 16 query heads, 8 key heads and 8 value heads, 256 floats each. The launch has one block per head per token: grid = (16 + 2·8, tokens). Query and key heads get the norm and the rotation; value heads are only converted to f16 and copied into the cache. Select a head.

Why it is built this way

    

      

        
Why lanes own columns 4l and 128 + 4l

        
RoPE in the NeoX layout rotates dimension i together with dimension i + 128. If a lane owned 8 consecutive dims, the partner of each value would live in another lane, and every rotation would need a shuffle. Giving lane l the four dims 4l–4l+3 and their partners 128+4l–128+4l+3 keeps every pair inside one thread. Both halves are still loaded as one float4 each, and a warp reads 512 contiguous bytes per half.

      

      

        
Fusing three jobs into one launch

        
Norm, rotation and the cache write all touch the same 1 KB per head. Doing them in one kernel reads each head once and writes it once (plus the f16 cache copy), instead of three round trips through memory. Value heads skip straight to the copy, so the launch also replaces a separate "append to cache" kernel.

        
Local layers keep a ring of 1024 + 128 = 1152 cache slots (the window plus one prompt chunk); global layers keep all 8192. The slot is pos % slots.
