Llama 3.1 · llama31.ptx (an older version in qwen35.ptx) · prefill: int8 tensor cores, 64 rows × 64 tokens per block

Inside gemm_q

When a prompt is processed, up to 512 tokens go through each matrix at once, and this kernel does the product. Each block computes a 64-row × 64-token tile of the output. It walks the inner dimension 64 values at a time: the 256 threads decode the weight slice with unpack16 (any of the 9 formats of mv_q) into int8 in shared memory, copy the int8 activations next to it, and then every warp runs mma.sync.m16n8k16 on the tensor cores: exact int32 dot products of 16 values, which the kernel scales into float sums. Every token's result is computed in the same order whatever its neighbours, so splitting a prompt into different chunks gives bit-identical logits.

Y[t][r] = Σb dₓ[t][b] · (s₀[r][b] · dot₀ + s₁[r][b] · dot₁) + m[r][b] · dₓΣx[t][b] + resid[t][r]   // dot_h = Σ over 16 values of q·x, int32 from one mma

The grid: one block per 64 × 64 tile

Columns of tiles are 64 tokens, rows 64 weight rows. blockIdx.x runs over the token tiles, so the blocks launched back to back share one weight tile and its bytes come from L2 after the first: each weight is read from memory about once per launch, and decoded once per token tile. Two mma per 32-value block

    

      

        
Why not one m16n8k32

        
The int8 tensor-core instruction also exists as m16n8k32, which takes a whole 32-value block in one go, and Qwen 3.5's version of this kernel uses it. But Q3_K and Q6_K have a different scale for each 16 values, and a scale can only be applied after the integer sum. So the kernel issues two m16n8k16, one per half, with A fragments {a0, a1} (values 0–15 of rows g and g + 8) and {a2, a3} (values 16–31), and B fragments b0 and b1. The two int32 results c and e get their own scales: acc += c·(s₀dₓ) + e·(s₁dₓ) + m·(dₓΣx).

        
A warp owns 16 rows × 32 tokens: one A fragment pair per block, four n-tiles of 8 tokens, so 8 mma and 48 FMAs per 32 values, and 16 float accumulators per lane (c0–c3 of 4 n-tiles).

      

      

        
Bank-conflict padding

        
A fragment load reads 4 bytes at row g (0–7) and column 4·t4 (t4 = 0–3) of the tile, for the 32 lanes at once. With 64-byte rows, rows g and g + 2 would start in the same bank. With 80-byte rows (20 words), the 32 lanes hit banks (20g + t4) mod 32: 0–3, 20–23, 8–11, 28–31, 16–19, 4–7, 24–27, 12–15, all different. The 16 padding bytes per row cost 2 KB of the block's 12.5 KB of shared memory.

      

    

  


  

    

      
The Qwen 3.5 version

      
qwen35.ptx has the first version of this kernel, with the same tiles, loader roles and padding; the Qwen 3.8 engine (and llama31.ptx after it) generalized the weight side.

    

    

      

      

        
Where the time goes

        
Llama 3.1's prompt runs at 2,260–2,490 tokens/s against llama.cpp's 5,300–5,500 on the same file. The kernel loads a k-step, waits, computes, waits: nothing overlaps the global loads with the mma (no double buffering, no cp.async). The 64 × 64 tile is small for a 28,672-row matrix, and the weights are decoded again for every token tile. The scaling (7 float instructions per accumulator per 32 values) also competes with the tensor cores for issue slots. These are the obvious next steps; the kernel's job here is to be exact and format-agnostic.
