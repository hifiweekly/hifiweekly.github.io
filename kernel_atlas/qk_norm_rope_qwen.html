Qwen 3.5 · qwen35.ptx · one warp per head

Inside qk_norm_rope, the Qwen version

In Qwen 3.5's 8 attention layers, every query and key head is normalized on its own (RMSNorm over 256 dimensions), then only its first 64 dimensions are rotated by the token's position; keys and values go to the KV cache as f16. It has the same name and the same one-warp-per-head plan as Gemma 3's kernel, but different data layouts, so qwen35.ptx has its own version: q heads sit next to their output gates, the rotation pairs dimension i with i + 32, and those pairs fall in two different lanes.

x' = RoPEpos( x / √(Σ x² / 256 + ε) · w )   // pair (i, i+32) for i < 32 rotated by pos · 10−7i/32 (base 10⁷); dims 64 … 255 left as they are

The grid: 24 heads per token

The stacked q | k | v projection writes 10,240 floats per token: 16 query heads, each followed by its 256-float output gate, then 4 key heads and 4 value heads. The launch has one block per head per token, grid = (16 + 2·4, tokens), and each block finds its head inside that row. Gates are skipped: the attention kernel reads them later. Select a head.

Inside one head

The 256 values are drawn as 32 columns, one per lane, and 8 rows: lane l owns dims 8l to 8l+7, which it loads as two float4 (32 consecutive bytes). Why it is built this way

    

      

        
Why lanes own 8 consecutive dims, and one shuffle

        
Gemma 3 rotates all 256 dims, pairing i with i + 128, so its kernel gives lane l dims 4l… and 128 + 4l… and every pair stays in one thread. Here the pairs are (i, i + 32) and cover only dims 0–63. Splitting the rotary dims like Gemma's would leave lanes 8–31 needing a different mapping. Instead every lane loads 8 consecutive floats, and the warp reads the head's 1 KB as one contiguous run. Lane l ^ 4 holds the 8 partners of lane l's values, so one round of 8 shfl.sync.bfly … 4 brings them over. Every lane runs the shuffle, because it is warp-synchronous with a full mask; lanes 8–31 discard the result and branch straight to the store.

        
Lanes l and l ^ 4 load the same 8 cos/sin pairs (64 bytes) and each computes its own half of the rotation: the low lane x cos − x′ sin, the high lane x′ sin + x cos.

      

      

        
Partial rotary: three quarters of a head carry no position

        
Qwen 3.5 rotates 64 of the 256 dims. Its IMROPE splits those 64 into sections for text, image height and image width, but for text every section gets the same position, so it reduces to ordinary NeoX RoPE on dims 0–63. Dims 64–255 are matched on content alone. With base 10⁷, pair 0 turns once every 6.3 positions while pair 31 needs about 3.8 × 10⁷ positions for a full turn, so the high pairs barely move in any real context.

        
The cos/sin table is [ctx][32][2], built on the host the way ggml builds it: the angle for pair i starts from the position and is multiplied by 10−7/32 = (10⁷)−2/64 once per pair, in float32.

      

      

        
The gate rides along

        
attn_q gives each head 512 values, [q | gate]. Rather than split them into two buffers, the kernel addresses q head h at offset 512·h and k and v heads after the 8,192 query floats, using the row stride passed as p_stride. The gate half is never touched here; the attention kernel reads it with the same stride and applies σ(gate) in its final write.

      

      

        
A plain cache index

        
Gemma 3's sliding-window layers keep a ring of cache slots, so its kernel stores to pos % slots. All 8 of Qwen 3.5's attention layers attend to the whole context and the other 24 layers keep no KV cache at all, so the cache is indexed by the position directly: K[pos][kh][256] and V[pos][vh][256], 2 × 4 × 512 bytes per token per layer.
