SAM 3 · sam3.ptx · two kernels: block partial sums with f64 atomics, then normalize + ReLU

Inside gn_stats and gn_apply

SAM 3's pixel decoder upsamples the fused image features twice, from 72² to 144² to 288². After each 3 × 3 convolution comes a GroupNorm with 8 groups and a ReLU. A group is 32 of the 256 channels at every pixel of the map: at 288² that is 2.65 million values per group, normalized together. A row-wise norm like layernorm cannot do this; it is a reduction over the whole map. gn_stats spreads the map over all SMs. Each block sums its rows, and lane 0 of each warp adds the block's sums for its group to a global f64 accumulator. Then gn_apply turns the 8 sums into means and inverse deviations and normalizes, scales, shifts and clamps every value.

y[p][c] = relu( (x[p][c] − μg) / √(σg² + ε) · w[c] + b[c] ),  g = c / 32,  μg, σg² over all pixels p and the 32 channels of g   // ε = 10⁻⁵

Thread t = channel t, so warp g = group g

A gn_stats block has 256 threads, one per channel, and owns a contiguous range of pixels (rows of the [pixels][256] map). Each thread walks its rows down its channel and keeps a sum and a sum of squares in f32. Warp g holds exactly the 32 channels of group g, so one butterfly gives the block's totals for that group, and one lane adds them to the group's f64 accumulator. The map here is a toy of 24 × 24 pixels split over 6 blocks, with the real 8 groups. Pick a map size and click a block or a group.

Why it is built this way

    

      

        
Two launches, because the statistics need everything

        
No value of a group can be normalized before every value of the group has been summed, and the group spans the whole map. A single kernel would need a grid-wide barrier. Two launches give one for free: gn_stats finishes before gn_apply starts, in the same stream. The cost is one more read of the map (85 MB at 288²) and a memset of the 128-byte accumulator first. Each gn_stats thread reads its channel with a stride of 1 KB from row to row, but the 256 threads of a block read one whole row (1 KB, contiguous) together, so the loads coalesce.

        
The groups line up with the warps

        
Channels are contiguous within a pixel and a group is 32 consecutive channels, so with 256 threads per block thread t is channel t and warp g is group g. The per-block reduction is then a plain warp butterfly per group, with no shared memory and no barrier. The kernel checks nothing about that alignment: the host only launches it for maps of 256 channels and 8 groups.

      

      

        
f64 for the totals, f32 for the work

        
Each thread's own sum covers at most a few hundred values (rows / grid), which f32 handles. The group totals add 2.65 million values in an arbitrary order across 448 blocks. The variance comes from E[x²] − μ², two totals that nearly cancel when the mean is not small next to the spread. So the totals and that subtraction are done in f64 (atom.global.add.f64, div.rn.f64), 16 atomics per block. The figure above shows what an f32 total would lose on data like this. gn_apply converts each group's mean and 1/σ to f32 once per block, in shared memory; everything per value is f32.

        
Fused outputs

        
gn_apply writes f32 (needed after the first stage, whose output the next stage upsamples and adds) and/or f16 (after the second, as the input of the instance-embedding product). The ReLU is part of the same expression. After the first stage the f32 output overwrites its input in place.
