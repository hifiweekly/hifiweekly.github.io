gate ‖ up

The feed-forward half of a layer starts with two matrix products of the same normalized hidden state xn: the gate projection and the up projection, both from the model width to the wider feed-forward width. An activation is applied to the gate and the result multiplies the up value element by element, so unit j of the gate decides how much of unit j of up passes on to the down projection. The "‖" means the two weight matrices are stacked into one at load time: Gemma 3 and EmbeddingGemma 2 compute gate and up in a single launch that writes one row gu[t] = [gate | up]. gpt-oss keeps them apart ("×2 gate, up"), one launch each, over the 4 experts the router picked.

h[j] = act(gu[j]) · gu[F + j]   // gu = [Wgate ‖ Wup] · xn, one launch, 2F rows

Why one launch, and why gpt-oss still has two

Stacking is allowed because the pairing is fixed

Gate and up read the same xn, and the activation only ever combines gate unit j with up unit j. So at load time the engines copy ffn_gate.weight into rows 0 … F−1 and ffn_up.weight into rows F … 2F−1 of one quantized matrix (upload_q5(…, &gate_up, 0) and (…, F); upload_q8 in EmbeddingGemma 2). The matrix kernel neither knows nor cares where one ends: it writes a row of 2F floats, and geglu reads gu[t][j] and gu[t][F + j]. One launch instead of two, xn quantized and read once, and twice as many blocks in that one launch, which fills the GPU better when there are few tokens.

gpt-oss: separate tensors, separate biases, two buffers

In the gpt-oss file the experts' gate and up are separate tensors (ffn_gate_exps, ffn_up_exps), each with its own f32 bias, and swiglu_oai takes two pointers, gate and up, writing its result over gate. The same trick would work per expert: stack each expert's gate and up rows (and biases) into one 5,760 × 2,880 matrix, and mv_mxfp4 / gemm_mxfp4 would run once with twice the rows. Each launch already spans 4 experts × 2,880 rows, so the gain is one launch per layer, not more parallelism. The engine doesn't do it yet.
