Inside dequant_q4k

MiniMax-H3's diffusion transformer is 11.4 GB of Q4_K matrices: 4.5 bits per weight, which is why it fits in a 12 GB GPU at all. The engine keeps them in that format and never builds the f16 matrices whole. Before each product, this kernel expands a slice of up to 6,144 rows (64 MB of f16) into a scratch buffer, and gemm_f16 multiplies it at once, while the slice is still in L2. A Q4_K super-block is 144 bytes for 256 weights: an f16 scale and min, twelve bytes that pack a 6-bit scale and a 6-bit min for each of 8 sub-blocks, and 128 bytes of 4-bit codes. The block below is the model's own: the first 256 weights of block 0's q, k, v projection.

w = (d · scj) · q − (dmin · mj),  q = nibble (j & 1) of qs[32 ⌊j/2⌋ + l]   // sub-block j < 8, value l < 32; (sc, m) 6 bits each, as ggml's get_scale_min_k4

Why it is built this way

    

      

        
Expand, then multiply on f16 tensor cores

        
The language-model engines in this atlas multiply quantized weights directly: one token at a time, a matrix–vector product that reads each byte once is bound by memory, and decoding in registers is free. The diffusion transformer multiplies 541 tokens at once, so it is bound by arithmetic, and the fastest arithmetic on this GPU is f16 mma with f32 accumulation. Decoding inside the GEMM's inner loop would re-decode every weight for each of the 5 row tiles of 128 tokens; expanding once per slice costs one extra write and read of the f16 slice. Measured with nsys over four steps: the GEMMs take 74% of the GPU time, the dequant 23%, attention 1%.

        
Slices of 64 MB

        
matmul() in the host code walks a matrix in slices of ⌊64 MB / (2 · K)⌋ rows, rounded down to 128 (the GEMM's tile): 6,144 rows of the 5376-wide q, k, v projection, 2,304 of the 14,336-wide fc2. The scratch buffer is reused for every slice of every matrix, so the f16 copy of a 115-million-weight matrix never exists whole, and the GEMM reads a slice the dequant has just written.

      

      

        
A thread per sub-block

        
The 8 sub-blocks of a super-block share d, dmin and the 12 scale bytes but nothing else, so a thread per sub-block needs no cooperation: it reads 2 + 2 + 3 bytes of header, 32 code bytes as 8 aligned words, and writes 32 halves as 8 eight-byte stores. A 144-byte block starts 16-byte aligned (144 = 9 × 16), which is what lets the codes be read as u32 words. Two threads (j and j + 1) read the same 32 code bytes, one taking the low nibbles and one the high.

        
The 6-bit scales

        
Sub-blocks 0–3 keep their scale and min in the low 6 bits of bytes 0–3 and 4–7. Sub-blocks 4–7 take 4 bits from bytes 8–11 (low nibble scale, high nibble min) and their top 2 bits from the unused high bits of bytes 0–3 (scale) and 4–7 (min). The bit view on the right colors each bit by the sub-block it belongs to.

        
Q6_K

        
The text encoder's v and down projections are Q6_K: 210 bytes per 256 values, 4 low bits in ql, 2 high bits in qh, a signed 8-bit scale per 16 values. dequant_q6k is the same scheme with a thread per 16 values; since 210-byte blocks are only 2-byte aligned, it reads them byte by byte.
