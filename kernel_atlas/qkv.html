×3 q, k, v

In every launch-order list, the attention half of a layer begins with "×3 q, k, v": the same matrix kernel runs three times, each time multiplying the token's normalized hidden state xn by a different weight matrix. The three results are the query (what this token is looking for), the key (what this token offers to be matched on) and the value (what this token passes on when it is matched). They land side by side in one buffer row, qkv[t] = [q | k | v], which the next kernels normalize, rotate and attend over.

q = Wq·xn   k = Wk·xn   v = Wv·xn   // same input, three slices of one qkv row

What q, k and v are for: a 4-token toy

Why three launches and not one

It works because the output can be a column slice

The matrix kernels take a row stride ldy for their output. Each of the three launches gets the full qkv row width as ldy and a pointer offset to its slice (0 for q, the size of q for k, q + k for v), so the three results interleave per token without a copy. Every launch reads the same xn, which stays in L2 between them.

…and it could be one

Stacking Wq, Wk and Wv into one matrix at load time, as the engines already do for the feed-forward's gate ‖ up, would make it a single launch over all rows, writing the same qkv row. It saves two launches per layer and reads xn once. For the big generators the saving is small next to the weight traffic; for EmbeddingGemma 2 on short texts, where launch overhead dominates, it would matter more. None of the engines does it yet.
