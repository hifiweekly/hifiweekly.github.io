Inside mv_q8

While generating, the model handles one token at a time, so every weight matrix is multiplied by a single vector. That work is limited by how fast the weights stream from memory, not by arithmetic: each weight byte is used exactly once. mv_q8 gives each output row to one warp and arranges the loads so a warp always reads one contiguous kilobyte of weights at a time.

y[r] = Σb d[r][b] · Σj<32 q[r][32b+j] · x[32b+j] + bias[r] + resid[r]   // Q8_0: int8 q, one f16 scale d per 32 values; x stays f32

One block: 8 warps, 8 rows

The example is the query projection: 4096 rows × 2880 columns, so each row has 90 Q8 blocks of 32 values. The canvas shows the 8 rows of one thread block (one per warp) and their 90 blocks. Why it is built this way

    

      

        
Contiguous kilobytes

        
In each round, lane l reads the 32 bytes of block l + 32·round. Together the 32 lanes read 1024 consecutive bytes of the row, the best case for the memory system. Their activations are 32 × 128 consecutive bytes of x. All loads use ld.global.nc (read-only path), and since all 8 warps of a block, and all 512 blocks, read the same x, it is served from cache after the first read.

      

      

        
Keeping x in float32

        
The MXFP4 expert kernels quantize the activation to int8 and use integer dot products. This kernel does not: attention projections and the output head see the residual stream, whose outlier dimensions lose too much in 8-bit blocks. So each int8 weight is converted to float and multiplied by the f32 activation (dot4_s8: 4 × bfe.s32, cvt, FMA), and the block scale is applied once per 32 products.

        
Per row that is 2880 weight bytes plus 180 bytes of scales: 3 KB in, 4 bytes out.
