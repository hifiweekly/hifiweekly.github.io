Inside compact_logits

Top-k and top-p sampling need the best candidates in sorted order, which is awkward on the GPU and slow to do on the host over all 201,088 logits. But tokens far below the best one have essentially zero probability. This kernel keeps only logits within a margin of the maximum (8 temperature units: a weight of e−8 ≈ 0.03% of the best) and packs them into a short list with one global atomic counter. The host then sorts a few dozen or hundred entries instead of 201,088.

keep i ⇔ x[i] ≥ x[best] − margin  →  j = atomicAdd(&out[0], 1); if j < cap: out[2 + 2j] = i, out[3 + 2j] = x[i]   // margin = 8·T, then 16·T, cap = 16,384

201,088 logits, a few hundred candidates

The kernel runs as a grid-stride loop: 448 blocks × 256 threads = 114,688 threads, so each thread checks one or two logits. Each cell of the map is the 256 logits one block checks in one lap; the shading counts how many pass. Change the temperature to move the threshold.

Why it is built this way

    

      

        
One atomic per survivor

        
Only threads whose logit passes touch the counter, so a few hundred atomics compete instead of 201,088. The returned old value is the thread's private slot, so writes never collide and need no further synchronization. Each candidate is stored as one 8-byte pair (index, logit bits) with a single st.global.v2.u32.

      

      

        
The fallback ladder

        
The host zeroes the counter before launch, reads it back afterwards and sorts the list by logit, then by index; the order in the list depends on which threads reach the atomic first. For top-p it uses the full-vocabulary normalizer Z that sample_logits already computed, so it can tell when the nucleus reaches past the candidates. In that case, or when top-k asks for more tokens than were kept, it retries with a 16·T margin. If the count exceeds the 16,384-entry cap (only the first 16,384 are stored), it falls back to copying all logits.
