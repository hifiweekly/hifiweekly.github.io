Inside gdn_recur

The heart of a Gated DeltaNet layer. Instead of keeping every past key and value, each of the 32 heads keeps one 128 × 128 matrix S that maps keys to values. For every token it decays S by a learned gate g, corrects it toward the new pair (k, v) with the delta rule (write only what S does not already predict, scaled by b), and reads the output as Sᵀq. The tokens of a chunk must go in order, so the kernel loops over them; the parallelism is across heads and value columns. A block keeps its 128 × 32 slice of S in shared memory for the whole chunk.

kv = Sᵀk  ·  δ = (v − g·kv)·b  ·  S ← g·S + k·δᵀ  ·  o = Sᵀq / √128   // g = exp(softplus(α + dt)·a), b = σ(β); q, k L2-normalized by gdn_conv

One block, one chunk of tokens

The large grid is the block's slice of S as it sits in shared memory: column i is key dim i (0 … 127), row j is the value column owned by lane j. Above it are this token's k and q (key dims, shared by every lane, read as broadcasts); at the right, per lane, v, kv = (Sᵀk)ⱼ, δ and o. Why it is built this way

    

      

        
Columns are independent, rows are not

        
Everything a value column j needs is its own column of S plus the shared k, q and the head's two gates: kvj, δj and oj never mix columns. So one thread per column needs no reduction at all, unlike the attention kernels' butterflies. What does not split is the key dimension inside a column: δj needs all 128 rows of Sᵀk before any row can be updated, hence two passes over the column per token.

        
32 heads × 4 column groups = 128 blocks of one warp. With one warp per block, the only synchronisation is bar.warp.sync around the k and q stores.

      

      

        
Shared memory, laid out [i][lane]

        
A thread walks its column 128 times per pass. Kept as S[i][lane], the 32 lanes read 32 consecutive floats for every i: 32 different banks, no conflicts, and k[i], q[i] are single broadcast reads. The same layout makes the load and the final store coalesced: global S is [h][i][j], so row i of the block's slice is 128 contiguous bytes.

        
Registers would be faster still (128 floats per thread fit), but they cannot be indexed by a loop counter: the kernel would have to be fully unrolled. Shared memory keeps the PTX a short loop; this kernel is not where decoding spends its time.

      

    

    

      

        
Decode: a fixed cost per token

        
Decoding runs it with T = 1: the 24 layers read and write 2 MB of state each, 96 MB per token, about 2% of the 5 GB of weights the matrix kernels read. Unlike attention, the cost does not grow with the context: token 100,000 costs the same as token 10.

      

      

        
Prefill: the sequential part

        
For a 1,282-token prompt the 72 launches (24 layers × 3 chunks of up to 512) take 51 ms, 12% of the prompt time, because each block walks its tokens one by one with only 128 warps in flight. llama.cpp's version (14 ms) rewrites the recurrence in chunked form, as small matrix products that run on the tensor cores. The arithmetic per token here is fixed, though: a chunk boundary changes nothing, which is what makes this engine's cache reuse bit-exact.
